# ARC review lessons for future changes

This is the reusable guidance extracted from ARC's completed reviews. It records failures that actually occurred, the decision that prevents each failure, and the existing regression coverage. Dated reports retain the original evidence and severity; this document is the entry point for future implementation and review.

## How to use

Before generating or changing code, read the sections relevant to the affected behavior and inspect their linked tests. Identify the authoritative state, compatibility boundary and failure path before choosing a component, hook, service or library. During review, check the actual caller and observable effect; matching a checklist or passing a build alone does not establish correctness.

For a regression, prefer an observable test that fails before the fix. For a refactor, retain the existing assertions and contracts; do not regenerate fixtures merely to accept changed behavior. Run the affected checks from [the verification matrix](../AGENTS.md#verification), and report what was exercised. Unrelated sections do not require extra work or approval.

## Maintainability lessons and contract guards

These are structural findings and compatibility requirements, not additional claims of production defects.

| Repeated maintenance risk | Decision to preserve | Existing evidence or owner |
| --- | --- | --- |
| Large files mixed grammar, execution, metadata, IO or unrelated UI lifecycles. Moving code alone could merely spread the same coupling. | Split around independently changing policies and migrate callers together. Keep cohesive algorithms together. Prefer typed records, named operations and short loops over positional arrays, nested ternaries or dense streams. Line counts and interface counts are observations, not acceptance criteria. | [Ownership map](maintaining.md), [architecture guard](../scripts/check_architecture.py) |
| A useful library appeared to replace handwritten code but differed in coercion, lazy evaluation, nulls, names or precision. | Check observable compatibility before substitution. Reuse existing Jackson, POI and HttpClient seams where appropriate. A new engine needs a differential corpus and an explicit version path for intentional changes to published rules; popularity alone is insufficient. | [Library assessment](reviews/2026-09-22-library-options.md), [expression compatibility](../backend/src/test/java/dev/arc/engine/expression/ExpressionCompatibilityTest.java) |
| Ambient evaluation state made reentrancy and reuse difficult to reason about. Resetting limits per child changes the contract; checking a deadline only after preparation allowed a slow child-definition read to be followed by another query after expiry. | Compiled expressions are immutable; each evaluation owns explicit context/budget. Nested collections and rules share operation/read limits and one monotonic deadline covering preparation and execution. Check before and after definition/configuration reads so an expired request cannot start later work; this does not interrupt JDBC already in flight. The deadline (`504`, `Kind.DEADLINE`) and the shared budgets (`422`, `Kind.LIMIT`) are not recoverable: field/case context keeps their message, and neither source `DEFAULT` nor `IFERROR`/`ISERROR`/`ISERR`/`ISNA` may turn them into a result. Direct `@id:version(...)` Formula calls use the same graph session, including calls in source bindings and collection bodies; inactive lazy branches must not execute children. Disabling trace retention must not disable the step budget. Keep request values and counters outside shared compiled plans; any bounded shared plan cache is keyed by immutable ID/version pins. ## Verification lessons

- Test user-visible effects. An invalid Save may reject at the command boundary rather than disable a button; assert the visible error, absence of the write and unchanged server revision. A test should not force a particular implementation of a valid behavior.
- Exercise late success **and** late failure, selection changes, close/reopen, retry and keyboard entry points when affected. An immediate happy-path test misses the schedules that caused the draft-loss defects.
- Use unique IDs and display names for fixtures selected by label. Re-running a suite against the same disposable database must not create ambiguous locators. Wait for observable layout completion before measuring or clicking an edge; arbitrary timing is not a contract.
- Remove Playwright routes before the navigation that should run unrouted: a request that starts while `page.unroute` turns interception off can stay paused forever, which left "Loading rule…" on screen in about a third of `editor-command-lifecycle.spec.ts` runs. A completion accepted with Tab resolves its snippet arguments from the node scope at that moment, so a test that types an `@` call waits for the `/api/variables` read of the typed text before accepting it.
- Use a clean Java build after package/class moves so stale compiled Spring beans cannot mask the real result. Remove obsolete imports, entry points and cross-test helper dependencies together with the move. `clean` removes compiled output, not obsolete `.java` files: restoring deleted main or test sources can still break compilation, and `spring-boot:run` also compiles tests. The native launcher reports untracked sources at paths deleted in available Git history; it preserves files and ordinary new sources. Inspect reported files and back up needed edits before moving obsolete copies outside the source directories. Coverage: [native startup diagnostics](../scripts/check_dev.test.mjs). See [startup troubleshooting](../README.md#troubleshooting-native-startup) for the distinction and history limitations.
- Use a separate Compose project, ports and database volume for tests that write fixtures. Clean up only that project. Do not validate against the user's working database. `frontend/playwright.config.ts` defaults `baseURL` to `http://localhost:3080`, the developer's own stack, so set `ARC_WEB_URL` for every Playwright run that can include browser tests, including spec files that mix pure and browser tests such as `tests/layout.spec.ts`; `npm run test:unit` is the only command that is safe without it. The smoke scripts likewise default to port 8080 unless `ARC_API_URL` is set.
- Check web-server behavior against the built image, not the Vite dev server: cache headers, 404 for missing hashed assets, gzip and proxy timeouts exist only in `frontend/nginx.conf`. A dependency such as the api container can be recreated with a new address; test that the proxy still reaches it without restarting web. `scripts/smoke.py` checks the HTTP boundaries on a live stack: an oversized body on a matrix-parameter path returns `413`, duplicate rule and source IDs return `409` with their messages, an unknown source's versions return `404`, a padded catalog search matches the trimmed one, a decimal result is written as `100` in the raw response text, a NUL character in a name returns `422`, and a `1e100` default (which PostgreSQL stores as a 101-digit integer) saves again and previews.
- A stylesheet change can move declarations in the cascade without any visible test failure. When a stylesheet moves into a lazy chunk it loads after the application styles; the React Flow move was checked by comparing the computed styles of all 502 elements of an editor page in both orders. For a refactor, record computed styles before and after with the opt-in [style equivalence spec](../frontend/tests/style-equivalence.spec.ts) (see [the style workflow](maintaining.md#styles)) and keep the always-on [cascade check](../frontend/tests/style-cascade.spec.ts) green.
- Distinguish static source assessment, unit behavior, real HTTP/database checks and browser workflows in the completion report. Do not claim a candidate library was exercised when it was only inspected, or that zero findings guarantees zero remaining bugs.
